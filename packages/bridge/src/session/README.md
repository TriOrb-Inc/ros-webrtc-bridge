# Session core

These are independent boundary modules that do not connect to ROS or WebRTC. `CommandGuard` manages leases and publisher handles; `DeliveryQueue` manages pending output for one peer. These are internal APIs for the session layer, not a public wire protocol.

Call `CommandGuard.openSession(epoch)` for each authenticated connection and `openHandle(sessionId, topic)` with the fully qualified ROS Topic name resolved by configuration and remapping. `authorize(identity, phase)` must explicitly return `true` for each of `open`, `arm`, `receive`, and `publish`. Authentication tokens and configured Topic, direction, and type validation belong to the higher-level policy.

`arm` excludes other sessions from the same output Topic. Re-arming through another handle in the same session also invalidates the previous lease. `prepare` consumes the received sequence; the returned ticket's `publish` revalidates the deadline, authorization, epoch, lease, ownership, and publication sequence. A ticket is single-use regardless of success or failure. An SDK must not attach an old payload to a new lease.

Pass only a synchronous ROS publication callback to `publish`. Adapters that wait asynchronously inside that callback are unsupported. Higher layers must validate payload types/values and rates on receipt and immediately before synchronous publication; this module alone does not establish command safety. Callback failure does not roll back the sequence, and ROS API success does not establish controller completion.

`clock` returns nonnegative monotonic Gateway milliseconds without side effects. Do not re-enter guard operations from the clock. A command is rejected at exact deadline equality. The constructor requires positive safe integers for `maxSessions`, `maxHandles`, and `leaseMs`, supplied by the configuration loader; there are no implicit module defaults. Session revocation and handle closure release registrations. The guard cannot be reused after `close`. Bound externally retained tickets and payload memory through finite higher-level queues.

Pass the Topic-specific `command_guard.lease_ms` as the third argument to `openHandle(sessionId, topic, leaseMs)`. Omitting it uses the constructor's `leaseMs`. Overrides must also be positive safe integers and are fixed for the handle after registration. Registering multiple Topics in one guard supports both per-Topic deadlines and exclusive writers per output Topic. The configuration loader must reject contradictory settings across aliases for the same output.

`DeliveryQueue` requires `maxStreams`, `maxBytes`, `maxMessageBytes`, and per-stream `maxMessages`. `latest` allows exactly one message and discards the old value on update. A new value that exceeds the peer's remaining byte budget is also dropped, returning `false`. Overflow on a `reliable` stream releases pending payloads, stops the stream, and continues returning `slow_consumer`. Recovery requires `closeStream` and explicit re-registration. The higher-level session must reject old stream IDs and prohibit their reuse.

The queue copies nonempty encoded `Uint8Array` messages, including envelopes. The cumulative drop count is a `bigint`. The adjacent `router` controls priority and rates; `transport` bounds buffers after dequeue. Process-wide budgets and native callback backlog control remain unimplemented and require long-running and overload evaluation.
